# RTX 3090 Ti Windows USB 解锁与 MiniMax H3 测试记录

日期：2026-10-31，Asia/Shanghai。

这是一台 RTX 3090 Ti 电脑的 USB 自动启动解锁记录，以及 ComfyUI MiniMax H3 文生视频完整任务的单次前后对照。12 项中 10 项耗时减少、2 项耗时增加。全部任务合计由 7622.95 秒变为 4932.45 秒，耗时减少 35.29%；该合计受偏长任务明显影响，不能视为稳定或普遍的加速比例。

[中文 CSV 数据](2026-10-31-rtx3090ti-minimax-h3.zh-CN.csv) 包含全部正式项目、分组合计和总计。CSV 的 `记录类型` 用于区分明细与汇总，分析时不要同时加总两者。

## 来源与本分支范围

本分支基于 [Windows-GPU-UNLOCK](https://github.com/windows-GPU-UNLOCK/Windows-GPU-UNLOCK) 的固定提交 [`fcf7ab5ec99b4facb928d8bbe5ace91014183669`](https://github.com/windows-GPU-UNLOCK/Windows-GPU-UNLOCK/commit/fcf7ab5ec99b4facb928d8bbe5ace91014183669)。原始解锁工作来自 [Zagitta/gpu-unlock](https://github.com/Zagitta/gpu-unlock)，本次参考版本为 [`0ebdb1c6308b6a2072be5bf04513472942541956`](https://github.com/Zagitta/gpu-unlock/commit/0ebdb1c6308b6a2072be5bf04513472942541956)。保留上游作者归属和仓库的 [GPL v2 许可文本](../../LICENSE)。

Windows/UEFI 自动启动、显卡事务和逐机器验证机制来自 Windows-GPU-UNLOCK 上游。本次增量为以下五个 host 夹具、模拟和回归测试文件的修正：

| 文件 | 修正内容 |
| --- | --- |
| `internal-boot/boot/make-console-fixture.py` | 核对采集器的驱动映像、binding、版本和 Stop 函数地址四个字段；在 LoadedImage 协议范围内校验元数据及完整路径。 |
| `research/profile/test_local_topology.py` | 调整合成采集记录，输出四字段 driver 记录，并对齐路径首节点与后续节点的前缀格式。 |
| `research/profile/test_aggregate_topology.py` | 增加采集器格式、冲突字段、完整路径和协议边界的回归覆盖。 |
| `internal-boot/boot/test_aggregate_prepare.c` | 将所有权边界故障注入实际的唯一 NVIDIA 边，而非无关的第一条边。 |
| `internal-boot/unlock/tests/test_efi_transaction.c` | 为模拟 DMA 地址与真实 host 指针增加 4096 字节间隔，避免偶然地址碰撞。 |

本次没有修改生产 EFI/GPU 执行代码、寄存器常量、兼容性准入或支持硬件范围。所有 22 项 host 检查通过，`HardwareAccess=false`。这些检查与下述实机启动记录、应用计时分别提供不同证据，不能相互替代。本记录只覆盖下表中的这一台电脑，不表示所有 RTX 3090 Ti 或主板均受支持。

## USB 启动过程与实机证据

本机先完成两次冷启动只读采集，生成逐机器 LOCAL 配置，运行 22 项 host 检查，再构建匹配本机的自动 USB 启动包。详细构建和适配要求见 [构建文档](../BUILD.en.md)、[USB 自动启动文档](../HEADLESS-USB.en.md) 及 [新机器适配文档](../NEW-MACHINE.en.md)。

操作过程为完整关机、断电后从 UEFI USB 启动。上游 wrapper 提供启动初始的 Esc 跳过窗口，随后在 NVIDIA Windows 驱动绑定前检查冷启动状态、释放固件显示驱动、尝试一次解锁、验证并启动 Windows。释放显示驱动后屏幕可能停止更新或变黑。本文不附带可直接套用到其他电脑的 LOCAL 配置或 EFI 包。

本机手动 USB 启动已成功，之后将 USB 设为首选启动项。操作者报告再次完整关机、断电、开机；新的 UEFI 日志时间为 20:01:06，Windows 启动时间为 20:01:07。该结果说明本机可在开机时自动重新应用解锁，不能据此声称断电后解锁状态仍然保留。

以下为该次日志的公开摘录。复位后行只摘取 selector 字段，其余行保持原始内容：

## 模型与测量方法

采用从 ComfyUI 下载的官方 MiniMax H3 T2V 工作流。参考：[ComfyUI MiniMax H3 原生工作流说明](https://docs.comfy.org/tutorials/video/minimax/minimax-h3-native)。

| 用途 | 模型文件 |
| --- | --- |
| 主模型 | `minimax_h3_fl2va_pruned_int8_convrot.safetensors` |
| 文本编码器 | `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors` |
| 视频 VAE | `minimax_h3_video_vae_int8_convrot.safetensors` |
| 音频 VAE | `minimax_h3_audio_vae_fp32.safetensors` |
| 8 步 LoRA | `minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors` |
| 4 步 LoRA | `minimax_h3_fl2v_turbo_4step_v1.0_768p_comfyui_bf16.safetensors` |

全部正式任务为 8 秒、24 帧/秒、192 帧，种子为 `757358688076805`，Turbo 开启，LoRA 强度 1.0，尺寸选择器为 16:9、32 倍数。第 1 至 9 项使用 8 步 LoRA 和 8 步采样；第 10 至 12 项使用 4 步 LoRA 和 4 步采样。

三个自定义提示词用主题编号识别：2 为“巨鲸游过海底古城”，4 为“废墟中的巨型机甲苏醒”，7 为“列车穿过山间花海”。完整提示词在本地经过换行及首尾空白规范化后，已与任务参数核对一致。本文不发布提示词全文，因此无法仅凭公开材料精确重现相同提示词输入。

解锁前后均按相同顺序执行：0.6 / 8 步的主题 2、4、7，然后 0.8 / 8 步、1.0 / 8 步、1.0 / 4 步的主题 2、4、7。每项在两个阶段各测一次。初始计划提到 0.98 档，历史任务确认最终对应项目实际使用 1.0 档，因此此处按实际输入和输出分辨率记录。

两阶段均先做一次默认提示词、0.6 档、5 秒输入、8 步的热身，热身不计入正式成绩。解锁后还误跑过三条自定义提示词的 5 秒输入任务，输出 124 帧、约 5.1667 秒；按操作者要求排除，再重新生成正式 8 秒任务。额外三次试跑使两阶段的实际热身与缓存历史不完全对称。

正式任务全部成功完成，采样节点均未命中执行缓存。统一采用后台 `Prompt executed in ...` 的完整任务耗时，包含任务内模型移动、编译、采样及解码等环节，不能视为纯 Tensor 运算吞吐。日志显示时分秒时，换算为整秒，保留原有精度，不混入历史事件差值的小数。第 3 项基线采用日志 239.50 秒；最初口头记录的 239.49 秒不用于统计。

## 异常与解释范围

按操作者要求，解锁前后所有偏长的正式记录均原样计入，未剔除、替换或按步数估算。第 10 项解锁前的 2749 秒对总计影响很大。解锁后同主题的 4 步任务为 461.47 秒，仍高于其 8 步任务的 410.22 秒；第 8、11 项解锁后也明显更慢。这些结果均保留。

两个阶段日志出现 `_ProactorBasePipeTransport._call_connection_lost()` 回调异常，正式任务仍全部成功。现有日志不足以区分异常长任务中动态权重加载、编译与采样各自的耗时，也没有证据证明回调异常就是变慢原因。

这是单机、每项一次的完整应用任务对照，没有重复测量、置信区间或纯 BF16 GEMM 测试。热身与缓存历史存在上述差异，功耗、超频设置及完整启动命令未记录，无法将耗时变化唯一归因于解锁。没有进行长期稳定性验证，也不能将本机结果推广到其他显卡、主板或工作流。
